# Database & Persistence

## ORM Choice: Drizzle

Fit40 uses **Drizzle ORM** with PostgreSQL.

### Why Drizzle Over Prisma

| Criterion | Drizzle | Prisma |
|-----------|---------|--------|
| Schema definition | TypeScript files | `.prisma` DSL |
| Type generation | Inferred from TS schema | Generated client |
| Query control | SQL-first, explicit | Query builder, more abstract |
| Runtime weight | Lightweight | Heavier (generated client) |
| Complex queries | Full SQL control | Limited for advanced cases |
| Domain model separation | Natural (schema is just TS) | Tends to couple domain to Prisma types |
| Migrations | drizzle-kit generates SQL | prisma migrate |

**Decision rationale:**
1. **TypeScript-first schema** aligns with our strict TypeScript approach. No DSL to learn.
2. **SQL-first** gives full control over queries, which is important for fitness analytics (volume calculations, progression queries, streak calculations).
3. **No heavy code generation step.** Schema changes are just TypeScript changes.
4. **Better domain model separation.** Drizzle types are clearly infrastructure concerns. With Prisma, the generated client types tend to leak into the domain.
5. **Lightweight runtime** matters for serverless/edge deployments.

## Schema Location

All Drizzle schema definitions live in:

```
src/infrastructure/database/schema/
├── users.ts
├── profiles.ts
├── exercises.ts
├── programs.ts
├── workouts.ts
├── sessions.ts
└── index.ts          # Re-exports all tables
```

### Schema Rules

1. **One file per aggregate** or closely related tables.
2. **Table names:** snake_case, plural (`users`, `workout_sessions`, `exercise_logs`).
3. **Column names:** snake_case (`created_at`, `user_id`, `started_at`).
4. **Primary keys:** `id` column, UUID v7, generated by default.
5. **Foreign keys:** Always define. Named explicitly.
6. **Timestamps:** `created_at` and `updated_at` on every table. Use `timestamptz`.
7. **Enums:** Use PostgreSQL `text` with `CHECK` constraints or Drizzle's `pgEnum`. Prefer `text` + `CHECK` for flexibility.

### Example Schema Shape (illustrative)

```typescript
import { pgTable, uuid, text, timestamp, integer, real } from 'drizzle-orm/pg-core';

export const users = pgTable('users', {
  id: uuid('id').primaryKey().defaultRandom(),
  email: text('email').notNull().unique(),
  name: text('name').notNull(),
  createdAt: timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),
  updatedAt: timestamp('updated_at', { withTimezone: true }).notNull().defaultNow(),
});

export const workoutSessions = pgTable('workout_sessions', {
  id: uuid('id').primaryKey().defaultRandom(),
  userId: uuid('user_id').notNull().references(() => users.id),
  workoutId: uuid('workout_id').notNull().references(() => workouts.id),
  startedAt: timestamp('started_at', { withTimezone: true }).notNull(),
  completedAt: timestamp('completed_at', { withTimezone: true }),
  notes: text('notes'),
  createdAt: timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),
  updatedAt: timestamp('updated_at', { withTimezone: true }).notNull().defaultNow(),
});
```

## Repository Pattern

### Structure

```
src/infrastructure/database/repositories/
├── drizzle-user-repository.ts
├── drizzle-user-profile-repository.ts
├── drizzle-registration-repository.ts
├── drizzle-session-repository.ts
├── drizzle-workout-session-repository.ts
├── drizzle-training-history-repository.ts
├── drizzle-program-repository.ts
├── drizzle-program-enrollment-repository.ts
└── drizzle-exercise-repository.ts
```

### Rules

1. **Each aggregate root has one repository.**
2. **Repositories implement Application port interfaces.**
3. **Repositories map** Drizzle rows ↔ Domain objects.
4. **Repositories handle database errors** and translate them to application errors.
5. **No business logic in repositories.** Only data access and mapping.
6. **Repositories are the ONLY place** that imports Drizzle.

### Example Repository Shape

```typescript
import type { WorkoutSessionRepository as Port } from '@/application/ports/workout-session-repository';
import type { WorkoutSession } from '@/domain/entities/workout-session';
import type { WorkoutSessionId, UserId } from '@/domain/types/ids';
import { db } from '../client';
import { workoutSessions, exerciseLogs } from '../schema';

export class DrizzleWorkoutSessionRepository implements Port {
  async findById(id: WorkoutSessionId): Promise<WorkoutSession | null> {
    const rows = await db
      .select()
      .from(workoutSessions)
      .where(eq(workoutSessions.id, id))
      .limit(1);

    if (rows.length === 0) return null;

    const logs = await db
      .select()
      .from(exerciseLogs)
      .where(eq(exerciseLogs.sessionId, id));

    return mapToWorkoutSession(rows[0], logs);
  }

  async save(session: WorkoutSession): Promise<void> {
    // Map domain to DB row and upsert
  }

  async findByUserId(userId: UserId): Promise<WorkoutSession[]> {
    // ...
  }
}
```

### Mapping Functions

Each repository has explicit mapping functions:

```typescript
function mapToWorkoutSession(
  row: typeof workoutSessions.$inferSelect,
  logs: Array<typeof exerciseLogs.$inferSelect>
): WorkoutSession {
  return {
    id: row.id as WorkoutSessionId,
    userId: row.userId as UserId,
    // ... map all fields
  };
}

function mapToDbRow(session: WorkoutSession): typeof workoutSessions.$inferInsert {
  return {
    id: session.id,
    userId: session.userId,
    // ... map all fields
  };
}
```

## Database Access Rules

### No ORM in Components

**React components must NEVER import Drizzle or access the database directly.**

```
❌ src/features/workouts/components/WorkoutList.tsx imports drizzle
✅ src/features/workouts/components/WorkoutList.tsx receives data via props
```

### No ORM in Domain/Application

**Domain and Application layers must NEVER import Drizzle.**

```
❌ src/domain/services/progression.ts imports drizzle
❌ src/application/use-cases/complete-workout.ts imports drizzle
✅ src/application/use-cases/complete-workout.ts uses WorkoutSessionRepository port
```

### Query Rules

1. **Use explicit `select()`.** Do not fetch all columns when you need a subset.

```typescript
// ❌ Over-fetching
const users = await db.select().from(users);

// ✅ Explicit selection
const users = await db
  .select({ id: users.id, email: users.email, name: users.name })
  .from(users);
```

2. **Avoid N+1 queries.** Use joins or batch loading.

```typescript
// ❌ N+1: one query per session
for (const session of sessions) {
  const logs = await db.select().from(exerciseLogs).where(eq(exerciseLogs.sessionId, session.id));
}

// ✅ Single query with IN clause
const logs = await db
  .select()
  .from(exerciseLogs)
  .where(inArray(exerciseLogs.sessionId, sessionIds));
```

3. **Use transactions for multi-step mutations.**

```typescript
await db.transaction(async (tx) => {
  await tx.insert(workoutSessions).values(sessionRow);
  await tx.insert(exerciseLogs).values(logRows);
  await tx.insert(setLogs).values(setLogRows);
});
```

4. **Use indexes on foreign keys and frequently queried columns.**

## Transactions

### When to Use

- Creating a `WorkoutSession` with its `ExerciseLog` and `SetLog` children.
- Enrolling in a program (create enrollment + update program stats).
- Completing a workout (update session + update progression + update streak).

### Rules

1. **All changes to an aggregate happen in one transaction.**
2. **Cross-aggregate changes** should be in a transaction if consistency is required.
3. **Keep transactions short.** Do not include external API calls inside transactions.
4. **Handle transaction failures** at the repository level. Translate to application errors.

## Migrations

### Rules

1. **Migrations are generated by `drizzle-kit`.** Never hand-edit generated migration files.
2. **Migration files are committed** to the repository.
3. **One migration per logical change.** Do not bundle unrelated schema changes.
4. **Test migrations** against a copy of production data before deploying.
5. **Backward-compatible migrations** preferred for zero-downtime deploys.

### Workflow

```bash
# Generate migration after schema change
npx drizzle-kit generate

# Apply migration (development)
npx drizzle-kit push

# Apply migration (production)
npx drizzle-kit migrate
```

## Indexes

### Rules

1. **Index all foreign key columns.**
2. **Index columns used in `WHERE` clauses** frequently.
3. **Index columns used in `ORDER BY`** for common queries.
4. **Composite indexes** for common multi-column queries.
5. **Do not over-index.** Each index slows writes.

### Expected Indexes

| Table | Column(s) | Reason |
|-------|-----------|--------|
| `workout_sessions` | `user_id` | Find sessions by user |
| `workout_sessions` | `user_id, completed_at DESC, started_at DESC, id DESC` | Training-history keyset pagination (completed sessions, newest first) |
| `workout_sessions` | `workout_id` | Find sessions by workout |
| `workout_sessions` | `started_at` | Time-range queries |
| `exercise_logs` | `session_id` | Load logs for a session |
| `set_logs` | `exercise_log_id` | Load sets for a log |
| `program_enrollments` | `user_id` | Find enrollments by user |
| `program_enrollments` | `program_id` | Find enrollments by program |

## Constraints

### Rules

1. **NOT NULL** on all required fields.
2. **UNIQUE** on natural keys (email, etc.).
3. **CHECK** constraints for value ranges (RPE 1-10, weight > 0, reps > 0).
4. **FOREIGN KEY** on all relationships. Use `ON DELETE` appropriately.
5. **Database constraints are a safety net**, not the primary validation. Domain validation is primary.

### Example Constraints

```sql
-- RPE between 1 and 10
ALTER TABLE set_logs ADD CONSTRAINT chk_rpe CHECK (rpe >= 1 AND rpe <= 10);

-- Weight must be positive
ALTER TABLE set_logs ADD CONSTRAINT chk_weight CHECK (weight > 0);

-- Reps must be positive
ALTER TABLE set_logs ADD CONSTRAINT chk_reps CHECK (reps > 0);
```

## Relationships

### Rules

1. **Define foreign keys explicitly** in Drizzle schema.
2. **Use appropriate `ON DELETE` behavior:**
   - `CASCADE` for owned children (e.g., deleting a session deletes its logs).
   - `SET NULL` for optional references.
   - `RESTRICT` for references that should prevent deletion.
3. **No implicit relationships.** Every FK is declared.

### Expected Relationships

| From | To | ON DELETE |
|------|----|-----------|
| `profiles.user_id` | `users.id` | CASCADE |
| `workout_sessions.user_id` | `users.id` | CASCADE |
| `workout_sessions.workout_id` | `workouts.id` | RESTRICT |
| `exercise_logs.session_id` | `workout_sessions.id` | CASCADE |
| `set_logs.exercise_log_id` | `exercise_logs.id` | CASCADE |
| `program_enrollments.user_id` | `users.id` | CASCADE |
| `program_enrollments.program_id` | `training_programs.id` | RESTRICT |

## Database Errors

### Handling

1. **Catch database errors at the repository level.**
2. **Translate to application errors.** Do not leak Drizzle/PostgreSQL errors to use cases or UI.
3. **Log the original error** for debugging.
4. **Return typed errors** that use cases can handle.

### Common Error Translations

| DB Error | Application Error |
|----------|-------------------|
| Unique constraint violation | `DuplicateEmailError`, `AlreadyEnrolledError` |
| Foreign key violation | `ReferenceNotFoundError` |
| Check constraint violation | `InvalidDataError` |
| Connection error | `DatabaseUnavailableError` |

---

## Mapping Database Records to Domain Objects

### Rules

1. **Mapping is explicit.** Write mapping functions; do not rely on structural typing accidents.
2. **Mapping lives in repositories.** Not in use cases, not in components.
3. **Mapping is pure and testable.** No side effects.
4. **Handle nullable columns explicitly.** Map `null` to domain `null`, not `undefined`.
5. **Convert types at the boundary.** DB `timestamptz` → domain `Date`. DB `uuid` string → branded ID.

### Mapping Direction

| Direction | When | Where |
|-----------|------|-------|
| DB row → Domain object | Reading data | Repository `find*` methods |
| Domain object → DB row | Writing data | Repository `save`/`insert`/`update` methods |

## Connection Management

### Rules

1. **Single database client instance** exported from `src/infrastructure/database/client.ts`.
2. **Connection pooling** handled by the driver (e.g., `postgres` or `pg` with pool).
3. **No connection logic in repositories.** They use the shared client.
4. **Environment-specific config** via environment variables.

```typescript
// src/infrastructure/database/client.ts
import { drizzle } from 'drizzle-orm/node-postgres';
import { Pool } from 'pg';
import { env } from '@/lib/env';
import * as schema from './schema';

const pool = new Pool({ connectionString: env.DATABASE_URL });
export const db = drizzle(pool, { schema });
```

## Future Considerations

- **Read replicas** for heavy analytics queries (progress dashboards).
- **Connection pooling service** (PgBouncer) for serverless deployments.
- **Database-level functions** only for performance-critical operations, with domain logic still in TypeScript.
- **Partitioning** for large tables (e.g., `set_logs`) if volume grows significantly.
